# T1.6 · Constructor del prompt dinámico

**Fase:** 1 · **Quién:** 🤖 Sonnet · **Depende de:** T1.2 · **Tamaño:** M
**Rama:** `t1-6-prompt`

## Objetivo

Función pura que arma el system prompt, el mensaje de usuario y `max_tokens` para una llamada, pidiendo solo los campos que la empresa paga y que el QR no dio.

## Contexto (leer)

- `docs/especificacion.md` §8 completa (8.1 a 8.4). El texto de `BASE_PROMPT` se copia **literal**, con sus saltos de línea.
- `docs/plan/README.md` §4, decisión 9.

## Qué hacer

1. `server/src/ai/basePrompt.ts`: constante `BASE_PROMPT` idéntica a §8.1, con `{EMPRESA_NOMBRE}` y `{EMPRESA_RUT}` como marcadores.
2. `server/src/ai/buildPrompt.ts`:
   ```ts
   buildPrompt({
     company: { nombre, rut },
     catalog,            // filas de field_catalog
     enabledOptional,    // claves opcionales activas
     preclassified,      // DocType | null
     qrData,             // campos que ya dio el QR (puede ser {})
   }) => { system: string; userText: string; requestedKeys: string[]; itemKeys: string[]; maxTokens: number }
   ```
   Reglas:
   - Campos pedidos = base con `source` que permite IA + opcionales activos, filtrados por familia del documento (`factura` / `devolucion`). Si `preclassified` es `null`, incluir los de ambas familias **y** `tipo_documento`.
   - Quitar las claves que ya trae `qrData` (`rut_emisor`, `tipo_cfe`, `serie`, `numero`, `total`, `fecha_documento`, y `cliente_rut` en devoluciones con QR).
   - Si el QR clasificó el documento, no pedir `tipo_documento`.
   - `revisar` siempre se pide.
   - Campos de producto (`is_item_field`): no se listan sueltos; se agrega una línea `- items: lista de productos, una entrada por línea, con las claves: codigo, descripcion, cantidad` (o las claves de producto activas: en facturas los `fact_item_*` sin prefijo — `codigo`, `descripcion`, `cantidad`, `precio_unitario`, `importe`; en devoluciones `codigo`, `descripcion`, `cantidad` + `ean`, `codigo_cliente`, `codigo_proveedor` si están activos). En facturas, `items` solo si hay algún `fact_item_*` activo.
   - Sección final con el formato exacto de §8.2 (`CAMPOS A EXTRAER` + `FORMATO`).
   - `userText`: con QR → `Tipo preclasificado por QR: <tipo>\nDatos ya leídos del QR, no los extraigas: serie A, número 6204, total 1994.94, fecha 2026-10-01` (solo los que haya); sin QR → `Sin QR de DGI: clasificá el documento`.
   - `maxTokens = min(1500, 150 + 2 × Σ est_out_tokens de los campos pedidos)`.
3. Snapshot tests (Vitest `toMatchInlineSnapshot` o archivos) para estos casos:
   - Factura con QR, solo campos base (debe pedir `cliente_rut`, `cliente_nombre`, `local`, `conformidad_nivel`, `sello_texto`, `notas_manuscritas`, `revisar`; nada de serie/número/total/fecha).
   - Factura con QR y todos los opcionales de factura.
   - Devolución sin QR (Devoto): sin preclasificar, debe incluir `tipo_documento` y campos de ambas familias.
   - e-Remito de Frog con QR: devolución, sin `rut_emisor`, `serie`, `numero`, `fecha_documento`.

## Criterios de aceptación

- `BASE_PROMPT` es idéntico al de la especificación (test que compara contra el texto de `docs/especificacion.md` extrayendo el primer bloque de código de §8.1).
- Los cuatro casos de test pasan y el prompt de una factura con QR y campos base tiene menos de 1.000 tokens (estimar con largo / 4).

## Fuera de alcance

La llamada a la API (T1.7).
