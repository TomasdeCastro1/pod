# T2.1 · Login por código al email y JWT

**Fase:** 2 · **Quién:** 🤖 Sonnet · **Depende de:** T1.1 · **Tamaño:** M
**Rama:** `t2-1-login`

## Objetivo

Login sin contraseña: el usuario pide un código de 6 dígitos por email, lo valida y recibe un JWT de 30 días.

## Contexto (leer)

- `docs/especificacion.md` §3 (login), §10 (`users`, `otp_codes`), §11 (`/auth/*`, `/me`, notas de límites), §13.1 (cuenta de revisión), §13.2.
- `docs/plan/README.md` §4, decisión 11.

## Qué hacer

1. `server/src/email/index.ts`: interfaz `EmailSender.sendCode(email, code)`; drivers `resend` (SDK `resend`) y `console` (para desarrollo: imprime solo que se envió, **nunca** el código salvo con `NODE_ENV=development`). Asunto y cuerpo en español, cortos.
2. `POST /auth/request-code { email }`:
   - Normalizar email (minúsculas, trim); validar con zod.
   - Generar código de 6 dígitos con `crypto.randomInt`; guardar **hash** (SHA-256 con `JWT_SECRET` como pimienta) en `otp_codes` con vencimiento a 10 minutos y `attempts=0`; reemplazar códigos anteriores de ese email.
   - Enviar el email. Responder siempre 200 con el mismo mensaje (no revelar si el email existe).
   - Si el email es `REVIEW_EMAIL`, no enviar nada (el código es `REVIEW_CODE`).
3. `POST /auth/verify { email, code }`:
   - `REVIEW_EMAIL` + `REVIEW_CODE` → válido.
   - Si no: buscar código vigente; sumar intento; más de 5 intentos o vencido → 401 y borrar el código; correcto → borrar código.
   - Crear el usuario si no existe (o reactivar si tenía `deleted_at`: crear uno nuevo, el anterior quedó anonimizado).
   - Devolver `{ token, user: { id, email, nombre }, companies: [...] }`. JWT HS256 con `sub=userId`, vencimiento 30 días.
4. Middleware `requireAuth`: valida `Authorization: Bearer <JWT>`, carga el usuario (rechaza si `deleted_at`), deja `req.user`.
5. `GET /me`: usuario + empresas con rol. `PATCH /me { nombre }` para que el usuario ponga su nombre (lo necesita el Perfil).
6. Rate limit con `express-rate-limit` en `/auth/*`: por IP, 10 pedidos cada 15 minutos para `request-code` y 20 para `verify`; además máximo 5 códigos por email por hora.
7. Logs: nunca loguear códigos, emails completos ni tokens.

## Criterios de aceptación (tests con supertest + PGlite + email falso)

- Flujo completo pide código → verifica → `GET /me` con el token.
- Código vencido, código incorrecto 6 veces y token vencido o alterado son rechazados.
- La cuenta de revisión entra con su código fijo y ningún otro email acepta ese código.
- El rate limit corta al superar el límite.

`DELETE /me` (T6.2). Empresas (T2.2).
